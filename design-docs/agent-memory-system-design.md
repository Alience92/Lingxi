## 问题根因

当前所有 Agent（包括 Claude Code）的记忆系统本质是 **"文件堆叠模式"**：

```
每次 session → 写 .md 文件
下次打开 → 加载 MEMORY.md 索引 → 关键词匹配 → 加载相关文件
```

致命缺陷：三个月后 200+ 行索引，80% token 浪费在无关记忆上。只有"更多文件"，没有"遗忘"。

这不是优化问题，是架构问题。

## 核心洞察

大厂没解决不是没想到，是**没动力 + 没数据闭环**。

1. **商业模式排斥**：好的记忆省 token → 省 token = 省收入
2. **记忆是基建不是功能**：没法 demo，不性感
3. **应用层数据闭环不在大厂手里**：用户修正/发布/反馈——这些数据大模型公司拿不到
4. **应用开发者有闭环但缺技术深度**：恰好是罕见交叉点

## 理想形态：不是文件系统，是数据库

```
当前（文件模式）：
  MEMORY.md 索引 → 30行全加载 → 跟今天无关的占 80% token

理想（数据库模式）：
  用户意图 → embedding 语义搜索 → 只加载最相关的 3-5 条
  跟今天无关的永远不被加载
```

## 记忆的三种形态

### 原始记忆（Raw Memory）
- 每次 session 自动生成
- 完整记录：上下文 + 决策 + 用户反馈
- 存完整但未整理
- **不直接加载**（太大、太多噪声）

### 活性记忆（Active Memory）
- 被多次引用、评判通过的
- 存：结构化摘要 + embedding 向量
- 每次 session 语义搜索，只加载相关条目

### 蒸馏规则（Distilled Rules）
- 反复出现的反馈模式被识别
- 存：一句话 + 权重
- 每次 session 必加载（~200 tokens，恒定体积）
- 新增一条就合并旧的一条，总体积不增长

## 记忆生命周期

```
诞生 → 初筛（三层评判第一层：关于什么？值得记吗？）
     → 拒绝：闲聊、重复、纯操作记录

     → 接受：
       ├── feedback 类 → 进入蒸馏观察池
       ├── project 类 → 标记项目/版本
       ├── reference 类 → 标记外部资源
       └── user 类 → 标记用户特征

     → 冷观察期（7天）：不加载，等被引用
     → 被引用 → 活性期 → 嵌入向量 → 可被语义搜索
     → 频繁引用 → 活性高
     → 长期未引用 → 沙漏衰减

     → 蒸馏：同类反馈 3+ 次 → 合并成蒸馏规则
     → 永久归档：沙漏 60 天+未引用 + 无蒸馏价值 → 删除
```

## 运行时架构

```
Session 启动：

  蒸馏规则（恒定 ~200 tokens）
  ├── 每次必加载
  └── 体积不变，新增合并旧的

  活性记忆（动态 ~500 tokens）
  ├── 根据用户意图做语义搜索
  └── 只返回最相关的 3-5 条

  原始记忆
  └── 不加载，只在被蒸馏或提升到活性层时才读
```

## 关键技术组件

### 1. Embedding 语义搜索
- 模型：BAAI/bge-small-zh-v1.5（384维，离线可用）
- 用户意图 → 向量 → 余弦相似度搜索记忆库
- 返回最相关的 3-5 条，不是关键词匹配

### 2. 三层评判（记忆版）

**第一层 - 归属判断**：关于什么维度？（feedback/project/reference/user）
**第二层 - 自洽性验证**：跟已有记忆一致吗？矛盾吗？
**第三层 - 引用验证**：被后续 session 引用了吗？产生了有价值的输出吗？

### 3. 沙漏衰减（记忆版）

```
7天内被引用   → decay_score = 1.0（新手保护）
7-30天未引用  → decay_score = 0.7
30-60天未引用 → decay_score = 0.3
60天+未引用   → 归档
长期不用       → 重新验证：用当前场景测试是否仍然成立
```

### 4. 蒸馏引擎

```
同类反馈出现 3+ 次 → 合并：
  "不要 mock 数据库"
  + "测试用真实数据"
  + "integration tests 踩过坑"
  → "测试必须用真实环境，不 mock 外部依赖"

原来 3 条 → 归档
1 条蒸馏规则 → 永久活性
```

## 为什么现在做不到（技术限制）

能做：
- 记忆文件格式（前端问题）
- embedding 语义搜索（BGE 模型已有）
- 蒸馏合并逻辑（prompt 工程问题）
- 状态标记（active/decaying/archived）

做不到（需改 Core）：
- 跨 session 自动触发（没有 cron）
- 后台衰减（没有持久化进程）
- 加载优先级（Core 决定加载什么，不是上层能改的）

## 理想 Agent 的样子

```
不是：
  通用大模型 + 记忆文件 + 越用越慢

而是：
  通用大模型
  + 向量化记忆库（可搜索，不是文件列表）
  + 蒸馏引擎（自动把回忆压成规则）
  + 活性系统（该忘的忘，该记的记）
  = 越用越懂你，越用越轻
```

## 从业态角度看

当前没有任何 Agent 产品做好这件事。不是技术问题，是**分工断层**：

- 大厂：没动力（token 消耗是收入），没数据闭环
- 应用开发者：有闭环但缺技术深度
- 这个交叉点恰好是最罕见的位置

## 讨论日志

本方案源于 2026-05-21 与 Claude Code 的深度讨论。设计者非计算机背景，通过：
- 数十亿 token 的实际使用体验
- 逻辑推理定位根因
- 想象力构建解法
- 自洽性验证方案

工作模式：描述设计意图 → Claude 验证技术可行性 → 写设计文档 → 作者审查 → 修正 → 最终定稿。

**核心理念**：不会写代码不是劣势——不会被"现有工具能做什么"束缚，只问"应该是什么"。这是所有好的系统架构的起点。
