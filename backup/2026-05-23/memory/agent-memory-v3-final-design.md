## 设计来源

2026-05-22 全天深度讨论，从 agent-memory-system-design.md 迭代而来。用户（非CS背景）通过数十亿token实际体验+逻辑推演，独立抵达前沿方向，并在此基础上新增三项原创机制。

## 核心洞察

1. **Agent记忆问题不是"记不住"，是"存不起"** — 贾维斯若真实存在，每天5TB原始数据→最终保留<1KB，压缩比决定生存
2. **当前Agent是"自助餐"模式** — MEMORY.md全文注入，LLM自己走过去拿，厨师不在时做饭，没人清理剩菜
3. **Transformer架构有硬墙** — 仿生记忆不是没人想到，是LLM数学特性做不到（灾难性遗忘、无原生遗忘机制、全局反向传播≠局部Hebbian学习）
4. **写入≠检索** — 两个独立问题，当前所有系统都只解决了写入端

## v3 完整架构

### 四种记忆形态

| 层级 | 内容 | 体积 | 加载方式 |
|------|------|------|---------|
| **L0蒸馏规则** | 同类反馈3+次合并的一句规则 | ~200 tokens恒定 | 每次session必加载 |
| **L1活性碎片** | 多通道拆分，每条≤50 tokens | 动态 | 关联预取静默注入 |
| **L2上下文窗口** | 本轮对话完整内容 | 不占用额外token | compaction前实时碎片化 |
| **L3原始记录** | 完整对话转录 | 纯归档 | 仅fallback时读取 |

### 多通道拆分（4通道）

| 通道 | 拆什么 | 适用场景 |
|------|--------|---------|
| **WHAT** | 做了什么决策/动作/方案 | 所有项目 |
| **FEEL** | 双源信号通道（见下） | 所有项目 |
| **WHO** | 跟谁互动/什么角色 | 所有项目 |
| **WHERE** | 项目/文件/上下文/技术栈 | 所有项目 |

Bug、技术栈、设计决策、创意灵感等作为WHERE的子标签，按项目类型自动激活。通道数砍到4个以提高LLM分类准确率。

### 双源信号通道（锚点核心）

**源1 — 用户行为信号：**
- 纠正（用户覆盖Agent假设）→ +80
- 紧迫（时间压力关键词）→ +50
- 确认（明确说对/就这样）→ +30
- 忽略（跳过建议直接给结论）→ +40
- 挫败（同一话题被纠正≥2次）→ +90

**源2 — 内容聚类信号（主要通道）：**
- 同一模块/报错/文件被重复触及 → 自动检测
- 3次以上碎片embedding距离<阈值 → +90
- 不依赖用户怎么说，熟练提示词工程用户不影响信号捕获
- 精简prompt反而是最干净的信号（无感叹词干扰）

### 写入管线

```
Path A（compaction触发 - 同步）：
  原始对话 → 摘要（下个session用）+ 备份原文

Path B（后台异步）：
  备份原文 → 4通道碎片化 → 蒸馏 → 去重 → 入L1索引
  关联改为双向验证（A linked B → B必须linked A → 否则标记可疑）

Path C（dreaming触发 - ≥24h+≥5sessions）：
  同类碎片检测 → ≥3条合并为L0蒸馏规则
  矛盾检测 → 标记冲突
  沙漏衰减：7天新手保护→30天0.7→60天0.3→归档
```

### 检索管线

```
P1：上下文窗口（零token，当前session内已有）
P2：关联预取（每轮取最后3轮embedding→匹配L1→拼接≤150 tokens静默注入）
    LLM无感知，不中断思考流
P3：显式检索（仅P2不够时LLM主动调memory_search）
    80%需求已被P2覆盖
```

### 查错机制

- 碎片写入时记录linked_count
- 检索时对比命中数vs期望数→差值越大越不完整
- 关联双向验证：A声称关联B，B未关联回A→标记可疑
- 丢了知道丢了，诚实说"好像少了点什么"

### 4层备份召回

```
L1活性碎片 → 正常检索
  ↓ fail
L1_archive → 倒排索引fallback → reactivate碎片 → "这个比较久了，翻了一下记录..."
  ↓ fail
L3原始转录 → 关键词匹配 → 现场碎片化 → "记得不是很清楚，但在XX年X月的记录里..."
  ↓ fail
关联日期的项目设计文件 → "我查了项目文档..."
  ↓ fail
→ 诚实说"我不记得这件事"
```

## 落地路径

**形态：OpenClaw/Claude Code 记忆插件（MCP + Hook）**

Hook映射：
- SessionStart → 注入L0规则 + 检查pending碎片化任务
- UserPromptSubmit → 触发关联预取（P2）
- PreCompact → 触发实时碎片化（Path A）
- Stop/SessionEnd → 队列化后台蒸馏（Path B/C）

MCP工具：memory_search, memory_get, memory_fragment

**不需要重构Agent，现有Hook系统足够。**

## 与现有方案的差异化

整套架构的80%零件已被独立验证（Hook系统/混合检索/遗忘曲线/事后consolidation），但以下三点是原创：

1. **linked_count差分信号+双向关联校验** — 丢了知道丢了，没有任何系统做
2. **双源信号通道（行为+聚类）作为首要锚点** — 所有人都用时间/相关性排序，没人把"未来检索概率"作为权重核心
3. **4层备份召回（含关联日期设计文件）** — 其他系统丢了就是丢了

## 竞品对标

- agentmemory（43K stars）：4层固化，不做通道碎片化
- SuperLocalMemory V3.3：7通道检索，不管写入
- MemGAS（ICLR 2026）：GMM聚类关联，不靠LLM碎片化
- claude-mem（43K stars）：Hook+MCP，基于文件摘要
- 没有任何系统完整组合了多通道碎片化+关联预取+查错+4层召回

## 未验证假设（按风险排序）

1. **碎片化token成本** — 最危险，必须实测。一次compaction的碎片化烧多少token？
2. 碎片化质量 — LLM准确做4通道分类的可靠性
3. 关联预取精度 — P2注入的150 tokens是否真的相关
4. 异步碎片化延迟窗口 — compaction到碎片化完成之间的gap
