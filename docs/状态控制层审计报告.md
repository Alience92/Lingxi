# 灵犀记忆系统 · 状态控制层审计报告

> 审计日期：2026-08-14（DSH 适配后）
> 审计对象：`D:\LingxiServer\src\`（灵犀记忆系统核心运行时）
> 审计方法：全量搜索所有 SQL 写入口（INSERT/UPDATE/DELETE），对照 state-gate.ts 的"统一写入入口"声明，评估状态控制层的完整性。

---

## 一、结论概要

**灵犀存在一个"半完整"的状态控制层**：核心架构意图明确（`state-gate.ts` 声明"所有核心状态修改必须通过此模块"），但**实际存在大量绕过统一入口的直接 SQL 写入**，且**部分核心状态存在双实现漂移**。结论：**控制层框架已建立但不完整，需要收敛**。

---

## 二、已建立的"状态控制层"架构

### 2.1 统一写入入口（state-gate.ts，V7 Phase A-2）

声明了 5 个一级入口，按状态类别分类：

| 入口 | 类别 | 功能 |
|---|---|---|
| `recordFragment()` | fact | 碎片写入（含 V7-A 压缩级别自动判定 + raw_evidence 溯源） |
| `recordRecall()` | fact | 召回日志 + recalled_count/decay 同步 |
| `recordFeedback()` | fact | 学习信号（dcgk_shadow_logs） |
| `rebuildActiveContext()` | derived | 工作记忆重建（带 `_meta` 可重建标记） |
| `runMaintenanceCycle()` | control | 后台维护周期（委托 MemoryOrchestrator） |

辅助机制：
- **writeLog 审计**：所有入口记录 `{category, table, caller, timestamp}`（`getWriteLog()` 可查）
- **`_state_meta` 表**：标记可重建的 derived 表（`markTableRebuildable()`）
- **状态类别四分类**：fact / derived / control / product

### 2.2 生命周期调度器（orchestrator.ts）

五阶段统一生命周期：
```
phase0 ingest（记录：信号+字图增量+聊天摄入+认知向量回填）
phase1 signal（分类：信号消费）
phase2 review（判定：checkDreamingTrigger 条件化）
phase3 maintain（维护：沙漏+衰减+蒸馏+条件化 dreaming）
phase4 proactive（输出：active-context 重建）
```
`runMaintenanceCycle` 委托 `runMemoryOrchestrator`，避免双实现漂移——这是收敛得最好的部分。

### 3.2 关键问题分类

**A. 双实现漂移（最需修复）**
- `active-context.ts`（旧实现，直接 UPDATE） vs `state-gate.rebuildActiveContext()`（新实现，带 `_meta`）——**两套代码写同一个 `projects.active_context` 字段**。orchestrator 用新入口，但 `updateActiveContext()`/`injectCareMessage()`/`injectAlerts()`（旧）仍可能被调用。格式不一致（旧无 `_meta`）会导致读方解析混乱。

**B. 无统一入口的核心状态（需新增入口）**
- **user_memory_models**（用户模型）：48 条，4 处直接写入，无 state-gate 入口——这是"懂你"核心资产，最该收敛
- **fragments 召回/衰减状态**：retriever/backup-recall/v7-long-term-memory 三处直接 UPDATE，与 recordRecall 的逻辑（decay=1.5 + active）不统一
- **lightweight_signals**：写入（extractor）与消费（dreaming-trigger）均无入口

**C. 合理豁免（不属核心状态控制范畴）**
- 灵络图（dcgk-store/observer）：独立认知图子系统，图内边权更新属其内部机制
- chat-history：手机壳宿主原始数据（ingest 源，非派生状态）
- activation_log/query_events：纯审计日志
- tools/eval 脚本：测试与基准，直接写自有测试数据可接受

## 四、完整性评估（对"是否有完整状态控制层"的回答）

### 已有 ✅
1. 统一写入入口（state-gate，5 个入口 + 审计日志）
2. 生命周期总调度（orchestrator 五阶段）
3. 状态类别四分类（fact/derived/control/product）
4. 可重建标记机制（_state_meta）
5. runMaintenanceCycle 已收敛到 orchestrator（无双实现）

### 缺失 ❌
1. **强制执行缺失**：state-gate 的"必须通过此模块"只是注释声明，无机制阻止绕过（未做 import 限制/未做写入代理）
2. **入口覆盖不全**：user_memory_models、fragments 状态更新、lightweight_signals 无统一入口
3. **双实现漂移**：active-context 新旧两套
4. **召回状态不统一**：三处直接 UPDATE decay_score，与 recordRecall 逻辑可能不一致

## 五、修复建议（按优先级）

| 优先级 | 项 | 建议 |
|---|---|---|
| P0 | active-context 双实现 | 让 `updateActiveContext/injectCareMessage/injectAlerts` 委托 state-gate 的 `rebuildActiveContext` 或统一到 orchestrator phase4，删除旧直接 UPDATE |
| P0 | user_memory_models 入口 | state-gate 新增 `recordUserModel()` 入口，v7-long-term-memory 收敛到它 |
| P1 | 召回状态统一 | retriever/backup-recall 的 decay/recalled UPDATE 改走 `recordRecall()` |
| P1 | lightweight_signals 入口 | state-gate 新增 `recordSignal()/consumeSignals()` |
| P2 | 强制执行 | 可选：封装 `getDb()` 为只读/写入双面，写面仅 state-gate 可访问（大改，评估成本） |
| P2 | 文档 | state-gate 头注释补充完整入口清单 + 豁免清单 |
