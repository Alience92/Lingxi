# 灵犀 BYOC 双通道网络架构

## 原则

- 用户数据**绝不**经过第三方服务器中转（信令交换除外）
- 移动端只发送脱敏的宏观状态摘要，不传输原始传感器数据
- 优先局域网直连，信令通道仅作为兜底

## 通道 A：局域网直连（首选）

```
手机 App ── WebSocket ──→ 电脑灵犀服务端 (192.168.x.x:11438)
                ↑
          mDNS 发现 / 扫码获取 IP
```

**延迟：** <10ms
**依赖：** 同一 WiFi 网络
**安全性：** 数据不离开局域网

**连接流程：**
1. 服务端启动时，通过 mDNS (Bonjour/Avahi) 广播服务 `_lingxi._tcp.local`
2. 手机 App 扫描局域网 mDNS 服务 → 获取 IP:Port
3. 或者：服务端生成配对二维码（含局域网 IP + 6 位配对码）
4. 手机扫码 → 建立 WebSocket 连接
5. 首次配对需在服务端确认

**自动回退：** 连接超时 2000ms → 切换到通道 B

## 通道 B：信令穿透（兜底）

```
手机 App ── WebSocket ──→ 信令服务器 ── WebSocket ──→ 电脑灵犀
         (仅交换连接信息)     (不存储消息)      (NAT 穿透)
```

**延迟：** 50-200ms（取决于中转跳数）
**依赖：** 用户自建轻量信令服务器（24元/月阿里云）
**安全性：** 信令服务器仅转发加密流量，不存储、不解密

**信令服务器职责（最小化）：**
1. 接收客户端的配对码和公钥
2. 匹配相同配对码的两端
3. 交换双方的 IP 地址和公钥
4. 后续通信：端到端加密 P2P（WebRTC Data Channel）

**信令服务器代码量：** ~100 行 Node.js WebSocket，无数据库，无日志持久化。

**连接流程：**
1. 手机 App 和电脑服务端各自连接信令服务器
2. 手机输入 6 位配对码 → 信令服务器匹配
3. 两端交换 SDP (Session Description Protocol) → 建立 WebRTC P2P
4. 如果 P2P 穿透失败（对称 NAT），使用信令服务器 TURN 中继
5. TURN 中继带宽成本：文字消息 < 1KB/s，几乎为零

## 自动回退逻辑

```
手机 App 启动
  ├─ 尝试通道 A（局域网直连）
  │   ├─ mDNS 扫描 → 超时 2000ms
  │   └─ 扫码/手动输入 IP → 超时 2000ms
  │
  ├─ 通道 A 成功 → 保持 WebSocket，心跳 30s
  │   └─ 心跳断开 → 重回尝试通道 A
  │
  └─ 通道 A 失败 → 切换通道 B
      ├─ 连接信令服务器
      ├─ 输入配对码
      └─ 建立 WebRTC P2P / TURN 中继
```

## API 接口

### POST /api/v1/context

移动端向服务端推送情境数据。详细 Schema 见 `src/types.ts` → `MobileContextPayload`。

```
请求：
{
  "timestamp": 1718500000000,
  "device_id": "a1b2c3d4-...",
  "activity_state": "walking",
  "inferred_mood": "fatigued",
  "location_context": "commute",
  "battery_level": 35
}

响应：200 OK { "ok": true }
```

### GET /api/v1/pair

服务端生成配对码（用于首次绑定设备）。

```
响应：{ "pair_code": "A1B2C3", "lan_ip": "192.168.1.100", "port": 11438 }
```

## 安全约束

- 移动端**绝不**发送：GPS 坐标、通知内容、联系人、短信、通话记录
- 情境数据仅在手机端本地计算后发送宏观标签
- 信令服务器不存储任何消息内容
- 配对码 30 分钟过期
- 每个配对码只能绑定一个设备
